## How to use this document

This is a reskin instruction, not a rebuild instruction. The reference site is https://vanlent.dev, the portfolio of Amsterdam-based creative developer Tim van Lent, nominated on Awwwards under Next.js, Three.js, Motion, Scrolling, 3D, Clean, and Portfolio. Map each pattern in this brief to the closest existing section in that inventory before touching styles. If a pattern below has no equivalent section in the OSINT tool, skip it — do not invent a new section or new content just to have somewhere to put the pattern.

Assume, unless the actual repository says otherwise, that the OSINT tool is a Next.js 15 app currently styled with Mantine v7 in a dark theme, since that is the standard stack this codebase has used elsewhere. If the real repository differs, adapt the implementation approach below to whatever styling system is actually in place rather than forcing Mantine in.

Why this direction is the right call for an OSINT product specifically: most reconnaissance and OSINT tooling defaults to a cluttered, node-graph or dense-terminal aesthetic — lots of panels, lots of noise, nothing considered. A restrained, near-monochrome, one-accent-color system with slow, deliberate GSAP-driven motion reads as precise and high-trust instead — it signals rigor and control rather than "startup dashboard," which is a real differentiator for a tool whose whole value proposition is disciplined analysis. That is the effect this brief is chasing: same content, dramatically more considered presentation.

## Layout and grid rhythm

The site reads as wide, editorial, and unhurried: generous outer margins, a strict column grid, and each major section commanding the full viewport height on desktop before yielding to the next — this is a slow, deliberate one-section-at-a-time scroll cadence, not a dense dashboard scroll where everything is visible at once. Oversized section headers sit above the content of each section. A distinctive numbered-eyebrow device precedes headlines throughout — small labels like "01. CREATIVE DEVELOPER" and "02. AMSTERDAM BASED" that function as a running breadcrumb down the page. This numbering pattern is worth carrying over: apply sequential numbered labels to whichever sections the OSINT tool already has, using the OSINT tool's own existing section names, not invented ones. Rows within list-style sections are separated by thin hairline dividers rather than boxed cards, and there are no heavy borders or drop shadows anywhere — it is a flat, ink-on-paper feel with color reserved for one accent used sparingly.

## Color and theme system

Qualitatively, the palette is a restrained, close-to-monochrome base — one dominant background tone, one neutral ink tone for text, and exactly one accent color used sparingly for links, CTA fills, and hover states — nothing else. Confirm the literal values via the live-inspection step above. If that inspection is not possible in a given session, fall back to a near-black background, an off-white primary text color, and a single muted accent (a restrained blue or a warm off-white functions well here), and flag the fallback as provisional pending confirmation. Whatever the final tokens are, they apply only to the OSINT tool's marketing-shell chrome — backgrounds, navigation, section headers, buttons, decorative dividers. Any functional or semantic color already in use in the OSINT tool for meaning — severity levels, risk scores, status badges, alert states, pass/fail indicators — must be left exactly as it is; those colors carry information and are not part of this reskin.

## Typography system

The type treatment is a clear two-tier system. Oversized display headlines (the kind of short, stacked lines like "Shaping / Concepts" and "Building / Experiences") are set in a large, tightly tracked, high-contrast display face with tight leading, while the small eyebrow numbers and nav items use a compact, uppercase, letter-spaced grotesk or mono treatment. Confirm the exact font-family via the same live DevTools inspection recommended above. Absent that, a confident geometric or grotesk sans for the display headlines paired with a compact mono or grotesk for labels and eyebrows is a safe, faithful direction. This new type system should be scoped to the marketing-style shell of the OSINT tool — headings, nav, labels, section eyebrows. Any existing data typography — tables, monospace output, code-like fields, terminal-style result panels — should be left on its current, legible typeface; readability of intelligence data must never be sacrificed for the sake of matching a portfolio's headline type.

## Header and navigation behavior

The header is fixed/sticky through the scroll, minimal in content: a small logo mark on one side, a menu trigger or anchor links on the other. The underlying pattern is almost certainly a full-screen overlay menu that opens via a height or clip-path reveal with the links staggering in one after another, rather than a conventional dropdown. Build that same overlay mechanism — trigger, full-screen reveal, staggered link entrance — around whatever navigation the OSINT tool currently has, using its existing nav labels. Do not add a language switcher or a decorative clock; those are specific to Tim's personal brand. If the tool already has a real theme toggle, view-mode switch, or live status indicator, give that existing control the same compact pill-shaped visual treatment instead of inventing a new one.

## Hero section choreography

On load, the entrance is staggered in a specific order: the small eyebrow label animates in first, then the headline reveals line by line — most likely a mask or clip-path reveal combined with a slight upward translate and fade per line, run through a GSAP stagger timeline — and only once the headline has settled does the supporting row (contact details, a CTA) ease in last. Reproduce this exact order — label, then headline lines one at a time, then supporting row/CTA — around the OSINT tool's own existing hero headline and subhead, verbatim content, new choreography only.

Every primary call-to-action button on the reference site shares one signature micro-interaction: the label sits inside a rectangle that is clipped shut and wipes open on hover or on scroll-into-view — a clip-path inset animating from fully closed toward fully open, producing a mask-style fill-in. Build this once as a small reusable button/link component and apply it to every existing primary action in the OSINT tool — whatever currently triggers a search, a scan, a login, a submit, or a key navigation step — keeping each button's existing label text exactly as it is.

The reference hero also cycles between a few alternate preview frames of the featured project, sliding horizontally via a translateX-driven mechanism. If the OSINT tool's own hero or landing view already shows a static product screenshot or dashboard preview, this same horizontal auto-advancing frame treatment can wrap it. If there is currently nothing to show there, do not force this in — it is optional, not a requirement.

## Repeating list / content-row pattern

The site's project list is a sequence of rows rather than a card grid: each row pairs a short category or role line with a two-to-three-sentence description and a paired media element, separated from the next row by a thin hairline rather than a border. Rows reveal on scroll one at a time as each crosses into the viewport — a short opacity-plus-slight-upward-translate animation, quick (roughly half a second to just under a second), eased out smoothly with no bounce or overshoot — and on hover the media element shifts subtly (a soft scale or crossfade) while the title picks up an underline or color shift. Apply this exact row rhythm, stagger, and hover behavior to whatever repeating list already exists in the OSINT tool — a list of data sources, scan modules, findings, integrations, or case entries — without adding, removing, reordering, or renaming a single existing entry.

## Capability list pattern

The services section is not a static grid of six always-visible paragraphs; it is a short list of labels where selecting or hovering one swaps a single shared description shown alongside the list, keeping focus on one capability at a time. If the OSINT tool has an existing feature or capability list, give it this same single-focus, hover-to-reveal-description mechanic, reusing the tool's existing feature names and descriptions exactly as written today.

## Stats counter pattern

Three inline statistics animate upward from zero to their final value the moment the section scrolls into view, driven by a scroll-triggered count-up with an eased rather than linear increment, over roughly a second and a half to two seconds. If the OSINT tool already surfaces any real numeric stats anywhere — records indexed, sources monitored, scans completed, alerts resolved, an uptime figure — wrap those exact existing numbers in this same count-up-on-scroll treatment. Do not fabricate new stats, new labels, or new metrics that do not already exist in the tool just to fill this pattern.

The testimonials are rendered as an infinite, seamlessly looping horizontal marquee of short cards — duplicated content driving a continuous translateX loop, pausing on hover. This is a generic, reusable mechanism, and it only has a place in the OSINT tool if there is already an analogous horizontal, continuously-updating list — a rotating alert feed, a source ticker, a log stream. Do not introduce client testimonials, quotes, or any comparable fabricated content into an OSINT tool; if there is no equivalent existing feed, skip this pattern entirely.

The closing section repeats the same clip-path-reveal heading and button treatment used elsewhere, followed by a two-column layout pairing organizational/meta information with a labeled form, and closes with fine-print legal links and a copyright line. Reuse this layout rhythm — numbered/eyebrow heading, two-column info-and-form split, legal footer — around whatever contact, support, or footer content the OSINT tool already has, keeping every existing field, legal link, and line of copy exactly as it is; only the spacing, type, and button styling change.

## Motion engine and implementation notes

Use GSAP with ScrollTrigger as the animation engine for every scroll-linked reveal, stagger, and the counter animation, and pair it with a smooth-scroll library — Lenis is the standard modern pairing with GSAP ScrollTrigger for exactly this kind of eased, one-section-at-a-time feel — set up once at the root layout so native scroll is intercepted consistently and stays in sync with ScrollTrigger. Keep individual entrance animations short: roughly 400 to 800 milliseconds per element, reserving the longer 1.5-to-2-second duration for the count-up numbers specifically, and use a consistent smooth ease-out throughout (a power2/power3-style curve) rather than anything elastic or bouncy — the reference site's whole character is considered and quiet, not playful. Every scroll-triggered animation needs a static fallback for users with reduced-motion preferences enabled, showing the final state immediately with no motion — this matters more, not less, for a professional analyst tool. If a Three.js accent element is added, keep it strictly decorative, cheap to render, and easy to disable outright if it ever competes with the performance of the OSINT tool's actual data views, especially any data-heavy tables or virtualized lists. All of this should be implemented as an additive motion/theme layer — shared hooks, wrapper components, and CSS variables layered around the existing components — rather than a rewrite of any existing data-fetching, state, routing, or business logic; no existing prop, API call, route, or line of copy should change as a side effect of this pass.

## Responsive behavior

On mobile, the header collapses into the same full-screen overlay menu pattern described above. The hero's label-then-headline stagger persists but stacks vertically. Any multi-frame preview slider becomes swipeable or auto-advances at the narrower width. Row-based list sections stack to a single column, keeping the same hairline separators and per-row reveal. Marquee and counter sections keep their motion but at a reduced element count or size if needed for performance. In every case, reuse whatever breakpoints the OSINT tool's frontend already defines rather than introducing a new breakpoint system.
